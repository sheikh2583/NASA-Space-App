# FireSense: technical review and hackathon assessment

Review date: **6 November 2026, Asia/Dhaka**. Source baseline: **`e97d49f`**. Documentation changes from this review do not alter code or scientific artifacts. Read the [architecture](architecture.md) and [scientific walkthrough](../science/harmonization-walkthrough.md) for the implementation.

## 1. Verdict

**Current hackathon readiness: about 6.5/10. Architecture/engineering: 8/10. Scientific readiness: 5/10.** These are the reviewer's judgments, not NASA scores, measurements or award probabilities.

FireSense is a substantial regional prototype with explicit source provenance, outage handling, holdout evaluation and evidence reporting. Its core calendar and harmonization workflow directly responds to the challenge. The main weakness is the gap between sophisticated scientific code and evidence that the current code/artifacts support the scientific claims. Conditional uncertainty fails in important activity groups, and recent statistical repairs do not have corresponding new human-run numerical results.

The defensible pitch is a regional historical burning-activity explorer with explicit uncertainty limitations. An operational fire-warning system, globally validated reconstruction or consistently calibrated 90% uncertainty service would overstate the evidence.

The instrument is **VIIRS**, not VIRAS. The official challenge is [Harmonization of MODIS and VIIRS Hot Spots](https://www.spaceappschallenge.org/2026/challenges/modis-and-viirs-hot-spots/).

Its official-domain indexed summary was retrieved on 6 November; direct full-page retrieval returned HTTP 502. The [HackAthlone mirror](https://hackathlone.com/challenges/modis-and-viirs-hot-spots) and [UAE organizer list](https://nasaspaceapps.ae/challenges) corroborated it. This review covers that summary, not an unseen detailed resource sheet.

The brief seeks a comparable active-fire calendar with geographic selection and historical exploration for monitoring audiences. The [official-domain Ajmer event page](https://www.spaceappschallenge.org/2026/local-events/ajmer/) lists Impact, Creativity, Validity, Relevance and Presentation. No final global or Bangladesh-specific weights were verified. Equal weighting below is this review's convention.

Eligibility and submission rules are separate from technical merit; this document does not decide them or reopen the team's organizer discussions.

## 9. Improvement priorities

These recommendations do not authorize bypassing the plan or running fits.

1. Keep the interval acceptance gap visible and reconcile artifact/report provenance with the revised science through the existing human workflow. If deferred, retain explicit limitations.
2. Observe one intended user selecting an area, identifying its central activity window, comparing a period and exporting evidence. Record actual usefulness and confusion.
3. Build a short evidence-led demo: sensor mismatch, harmonized regional calendar, one useful comparison, then the uncertainty limitation. A feature tour is weaker than a clear user decision.
4. Verify fast area/date/view changes, keyboard and mobile use, export errors, the deployed Git revision and served report contents.
5. Continue feature work through the plan. T14/T15 addresses whole-season anomalies; planned story/brief/recurrence work can support presentation but earns no current delivery credit. This review does not cut cards.
